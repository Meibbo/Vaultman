# Handoff — U121-027 live cells

**Branch** `claude/u121-025-026-027` · **worktree**
`.claude/worktrees/u121-commands` · **base** `origin/main` (1.2.0 stable) ·
**last commit** `b5176943`.

**The build currently synced to `plugin-dev` reintroduces the typing
micro-stalls.** Do not ship it. Step 1 below removes them.

## Read this first: the answer is already in the codebase

The dev asked why `cell_words` updates live while `mtime` does not, and whether
every cell would benefit from the words pipeline. **Yes — and the signal the
time cells need is already firing and being thrown away.**

`serviceStatisticsCache.ts` already subscribes to `vault.on('modify')`
(`:97-101`) and emits `file-stats-refreshed` carrying the changed paths
(`:166`). That event reaches `explorerFiles._handleStatsChange` on every note
edit. Until now the handler only acted on it when the sort was `words`/`tasks`
and otherwise returned — so editing a note left the mtime cell **and** an mtime
sort stale until an unrelated render came along.

The words path does the right thing and is the model to copy:

| Piece | Where | What it does |
| --- | --- | --- |
| Invalidation | `serviceStatisticsCache.ts:97` | `vault.on('modify')` → `invalidateFile` |
| Notification | `:166` | emits `file-stats-refreshed` with `paths` |
| Reorder check | `_statisticsSortNeedsReorder(paths)` | only re-sorts when the order actually changes |
| **Targeted update** | `_patchVisibleStatisticsCells(paths)` `:2289` | **queries rendered rows by `data-path` and writes the cell text straight into the DOM — no render, no rebuild, no re-sort.** Per-mode selectors, so tree, table and grid all work. |

That last row is the whole answer. It is a cell-level update pipeline that never
touches the render path, which is exactly what LivreUI needs and exactly what my
implementation failed to use.

## What I got wrong

I fixed the *symptoms* through the *render* path instead of the *data* path.
Every one of my fixes ends in `_render()` — rebuild, re-sort, re-decorate. That
is why the stalls came back: **the minute ticker runs a full `_render()` on a
timer.** The dev's own words point straight at it — "hasta que se hizo tu
refresco cada x tiempo".

Twelve hours went into this issue across several agents and the reason is
consistent: everyone patched the repaint, nobody moved the cells onto the
existing invalidate → notify → patch pipeline.

## Step 1 — stop the bleeding (do this first, then rebuild and hand the dev a clean build)

In `src/components/containers/explorerFiles.ts`, the interval registered right
after the `dragover`/`drop` listeners calls `_scheduleLiveRender`, which runs a
full `_render()` once a minute. Replace that call with a **text-only patch** of
the visible time cells (see step 2), or delete the interval outright and rebuild
if you want the dev unblocked in one minute.

Also re-measure the second suspect: the non-`'opened'` branch of
`_handleActiveFileChange` now repaints the tree window on every file-open.
It deliberately avoids `_render()`, but BT5-030 wanted that event silent, so it
is still a candidate. Bisect in this order — ticker first, file-open branch
second.

## Step 2 — the definitive fix

Generalize `_patchVisibleStatisticsCells` from "words and tasks" into a **cell
patcher keyed by cell id**, then feed it from three sources:

1. **`file-stats-refreshed`** — already arriving, already carrying the changed
   paths. Patch `mtime`/`ctime`/`opened` for those paths. This fixes the dev's
   "modified 4 notes, nothing updated" case, and it fixes the *sort* case too if
   you reuse `_statisticsSortNeedsReorder` to decide between patch and reorder.
2. **The minute ticker** — patch every visible relative cell instead of
   rendering. Keep the `_hasLiveTimestamps` guard so an idle or absolute-mode
   vault does nothing.
3. **`file-open`** — patch the opened path only. Cheaper than the tree-window
   render I added and it satisfies BT5-030 outright.

The BT5-089 open-shortcut fix (refreshing the moved node before
`treeView.render`) is correct as-is — that path genuinely reorders, so it needs
the model updated, not a DOM patch. Keep it.

**Sort is the harder half.** A DOM patch cannot fix a stale *order*. When the
new mtime changes the sort position, `_statisticsSortNeedsReorder` already
answers "does this require a reorder?" for words/tasks — extend it to time
sorts, and reuse `moveNodeToSiblingEdge` the way BT5-089 does for Last opened.
The dev explicitly asked for this: *"vamos a necesitar hacer algo tipo lo que
hicimos con last_opened, de que la nota abierta se le de prioridad"*.

## What is worth keeping from `b5176943`

- **The settings subscription.** `plugin.onSettingsChange` shipped in 1.2.0 with
  zero subscribers — every toggle broadcast into the void. This is a real fix.
- **`_scheduleLiveRender`** as the single coalescer for sources that genuinely
  need a full render. Do not let it become the answer to everything; that is the
  mistake this handoff exists to correct.
- **`isLiveTimestamp` / `LIVE_TIMESTAMP_TICK_MS`** in `logicRelativeTime.ts`,
  pure and tested (12 tests).
- **The flag lives in `_formatDateCell`**, not in the tree decoration pass —
  grid and table never run that pass. The first version had this wrong and would
  have failed silently in two of three view modes.
- **The Cells section** on Panel: Explorer, and the finding that
  `timestampRelative` is *not* the only cell-shaping setting:
  `addonCellStyle`, `orderCellsByActivation`, `filesHoverInfo`, the scrub
  name-cell options and `gridEditableColumns` are the rest, still scattered
  across other pages. Grouping those is an open UX call the dev has not made.

## Guards

`test/unit/livreUiCellRefresh.test.ts` (new, 5 tests) pins the LivreUI
invariants structurally, in the style of BT5-031's icon guard. **Update them
when you move to the patch pipeline** — several assert the render-path shape
this handoff replaces.

Two existing guards were widened and both deserve a second look, because they
encode contracts I bent:

- `lastOpened.test.ts` — BT5-013's early-return shape.
- `explorerViewportRefresh.test.ts` — **BT5-030's "no panel render on
  file-open"**. I narrowed it to "no `_render()` in that branch". If step 2 lands
  properly, restore the original stricter assertion.

**No perf guard exists for this path.** The suite is 1021/1021 green and did not
catch a regression the dev felt within minutes. Worth adding one — that gap is
part of the finding, not an aside.

## Policy

`.agents/docs/architecture/policies/livreui.md` (written this session, also
copied into the worktree) records the rule and, more usefully, *why this keeps
recurring*: every instance was born in a fast path, because the point of a fast
path is to skip work and the decoration pass is the easiest thing to skip by
accident. Codex hit the same class independently. Update its "how to comply"
section once the patch pipeline exists — right now it points at the coalescer,
which step 2 demotes.
